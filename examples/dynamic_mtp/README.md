# 910B4 动态 MTP 与解码整图

在同一 V2 推理进程中，根据本实例的输入长度和运行、等待请求数，选择每步生成的草稿 token 数 K（0～3）。保留 `FULL_DECODE_ONLY`。图查找会按验证宽度寻找兼容的整图。降到 K=0 时，丢弃待验证草稿，并在 GDN/Mamba 状态预拷贝中归位已接受的状态。

请求首次进入调度器时计算状态块预留上限，每个调度步按批内最低上限约束 K。K=0 的新请求仍预留一个临时状态槽。跳过草稿的旧请求在结束前保持在普通解码路径，新的请求在负载回落后可以重新使用推测解码。

## 使用

需要 vLLM 和 vLLM-Ascend **0.30.0**、GNU `patch`，以及可用的 Ascend 环境。请用同一个已安装 vLLM 的 Python 环境执行启动脚本。启动脚本校验相关模块的源码摘要，在运行目录构建补丁模块，再将它们注入 vLLM 进程。默认直接使用原生 `vllm serve` 的服务不受影响。

以下命令展示了必要参数。模型、量化和其他参数按实际部署填写。

```bash
cd examples/dynamic_mtp
python3 launch.py --state-dir /tmp/ascend-dynamic-mtp --policy policy.example.json -- \
  serve /path/to/qwen-27b-w8a8 \
  --tensor-parallel-size 1 --max-num-seqs 128 --no-async-scheduling \
  --compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[1,2,4,8,16,32,64,128,256,512]}' \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3,"num_speculative_tokens_per_batch_size":[[1,1,3],[2,3,2],[4,7,1],[8,128,0]]}'
```

`policy.example.json` 的外层键是输入 token 档位，内层键是**单实例**并发上限，对应的值是目标 K。输入长度选择比例上最接近的档位，并发向上取表内档位，超过最大档时使用该行最后一档。运行时的实际 K 还受批内请求状态约束。服务日志 `Dynamic MTP selected K=...` 展示调度器的选择。

2026-11-24 的 192 组 K2/K3 边界对照支持将 64-token 输入的 K3 上限扩展到单实例 24 并发，整机均衡分流时对应 48 并发。六组对照中 K3 均取得更高吞吐，其他推荐档位沿用此前表格。

## 验证范围

历史 910B4-1 真机测试覆盖 Qwen 27B W8A8、TP1、V2 同步调度和单机两个独立 TP1 实例。验证包含 K 切换、解码整图回放和逐 token 的定向正确性。自动选 K 仅在部分场景取得优势，持续高并发和首 token 尾延迟仍应按业务测试。示例策略来自测过的输入与并发档位，长输入和不同模型需要自行标定。TP2、异步调度以及与磁盘前缀恢复同时使用仍待验证。

本地测试可运行 `python3 -m unittest discover -s tests -v`。

## 实验选项 — GDN K2 索引优化

启动时在 `--` 前加 `--gdn-k2-indexing`，启用本实验分支的附加补丁。示例使用单卡 TP1、同步 Model Runner V2 和 `FULL_DECODE_ONLY`。双卡 DP2 用两个独立 TP1 实例。命令中的模型路径仍指向部署方自己的 checkpoint。

启动器会为 K=2 验证补充 12、24、48、96 位置的图尺寸，并为 32 个请求、每请求 3 个位置的整批保留专用图。仅当纯解码批次与捕获的请求数和验证位置完全一致时才使用三列 GDN 索引。其他形状沿用通用图。同一前向内，相同状态索引张量、起点张量和长度共用一份展平结果。每次前向重新建立映射，各层独立维护状态。

实验在 Ascend 910B4-1、Qwen3.8-27B W8A8 上先将 K 锁到 2，分别用正常请求与 profiler 验证。单卡 32 并发的目标图保持 96 个位置，快速路径让每步各 48 次的 `SearchSorted` 和 `Cumsum` 都降到零。单卡未开 profiler 的两轮整组输出吞吐均值从 742.37 升到 781.38 tok/s。31 并发的通用补齐图在索引共享后每步只剩各 3 次。受控 NPU 算子复测中，均匀和变长样例的输出与写回状态均逐元素一致。

双卡分别运行一个 TP1 实例，所有对照锁在 K=2，使用相同的输入与路由，固定输出 256 token，前缀缓存命中为零。每个配置两轮，表中为整机 64 并发的平均输出吞吐，单位为 tok/s。

| 输入 token | 动态 MTP，仅补图尺寸 | 动态 MTP，含 GDN 优化 | 原生固定 MTP2 |
| ---: | ---: | ---: | ---: |
| 64 | 1485.47 | 1582.55 | 1602.91 |
| 512 | 1134.94 | 1237.21 | 1247.46 |
| 2048 | 570.56 | 692.22 | 699.73 |

用本启动器及示例策略在同两张卡上依次提交整机 2、64、2 个并发请求。每卡日志都记录到 K3、K2、K3，68 个请求均完成 256 token 输出。每组结束后确认两台副本均无排队或运行中的请求。

这些吞吐数据用于隔离 K=2 的成本。实际业务的收益还取决于流量与选档策略。端到端贪心输出的哈希一致率随场景变化。2K 输入、64 并发时，原生固定 MTP2 的两轮也有输出差异，两轮之间的逐请求完全一致率为 5/64，这两轮交换了请求与卡的对应关系，同一轮内各配置使用相同路由。逐元素一致的结论限于受控 GDN 算子测试。

## 实验选项 — GDN Prefill 工作空间

在启动器的 `--` 前同时添加 `--gdn-k2-indexing --gdn-prefill-grouping`，启用独立序列分组。多序列 GDN Prefill 的总长度超过 4096 token 时，按完整序列边界分组，逐组调用现有 FLA NPU 算子并合并输出及各请求的最终状态。各序列内部保持原有执行方式。单个长序列和包含空段的批次走既有路径。

在 Ascend 910B4-1、Qwen3.8-27B W8A8、FLA NPU 26.9.1 的诊断中，原版在 27 条请求共 8000 token 的 GDN Prefill 批次分配工作空间失败。受控算子测试将该批次划分为 3904 和 4096 token 两组，峰值显存增量从 1415.25 MiB 降至 941.68 MiB，输出及最终状态逐元素一致。另一种 6656-token 批次也通过逐元素对照。

使用此分组原型，在双独立 TP1 实例、`gpu-memory-utilization=0.95` 下完成 190 请求的故障复现流量和另一轮 950 请求的完整突发流量，启动时每实例的 KV Cache 容量维持 417047 token。两轮均未发生 OOM。独立的工作空间实验中，190 请求组仍出现两条重复字符异常，950 请求组通过输出检查。

## GDN 验证长度缩小时的状态归位

FLA NPU 的 recurrent GDN 接口要求已接受位置计数落在当前序列的验证长度内。动态 K 降低时，历史已接受的位置有可能大于当前长度。旧补丁仅对降到单位置的情况做块内归位。本分支将归位条件推广到任意正验证长度小于历史已接受位置的情况。既有 GPU 预处理核标记块内复制，预复制核将正确的 recurrent state 与卷积窗口归位到基础槽，并将接受位置归一为 1。整个决策仍在设备端完成，跨块迁移继续使用原有流程。

在双独立 TP1 的同一故障复现序列中，原版 190 个请求有两条异常重复字符，并有一条实际请求出现已接受位置 4、当前验证长度 3。修正后 190 个请求全部通过输出检查，所采集的状态元数据均满足验证长度约束。另有 19 个真实 NPU 归位决策用例覆盖了 1～4 个位置、跨块、空调度和新状态。

块内状态复制测试覆盖两种卷积布局，卷积窗口和 recurrent state 的预期写回均逐元素一致。组合两项修正后，在 0.95 下分别重放 190 条短输入突发请求和 106 条 Agent 混合输入请求，覆盖此前三个异常输出样本，296 条请求均完成并通过输出检查。完整模型与原生固定 MTP 的贪心 token 序列可能存在数值执行差异，质量结论以本次故障复现和算子对照为准。

## 组合验收结果

2026-11-25 的组合验收总计 3114 条请求，包含三种流量的九次配对回放和 40 组同步提交的固定 K 对照。两张 910B4-1 各运行一个 TP1 实例，最大上下文 262144，HBM 利用率 0.95，输出 256 token，前缀缓存实测零命中。所有组通过请求完成、输出计数及异常重复字符检查。

| 输入 token | 整机并发 | 动态锁 K2 | 原生 K2 | 动态锁 K3 | 原生 K3 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 1 | 51.98 | 52.43 | 60.87 | 60.35 |
| 64 | 32 | 987.61 | 1001.48 | 1043.63 | 1050.97 |
| 64 | 64 | 1601.31 | 1588.90 | 1632.82 | 1637.10 |

| 2048 | 64 | 686.03 | 697.50 | 696.53 | 704.48 |

以上均为整组输出 tok/s，两轮中位数。同 K 时各点与原生档的相对差距绝对值在 1.67% 之内。

| 流量 | 动态 | 原生 K2 | 原生 K3 |
| --- | ---: | ---: | ---: |
| 短输入突发 | 1275.96 | 1274.86 | 1296.98 |

以上为峰值请求组的输出吞吐中位数，单位 tok/s。三套配置在对应场景提交完全相同的请求到达序列，均在规定时间内完成。动态策略在突发和升降并发中接近最佳固定档，Agent 长短混合中仍比固定 K2 低约 6.9%。ITL 的服务端直方图记录输出事件间隔，TPOT 为逐 token 平均解码延迟，两者都在本次实验中采集。

| 流量 | 动态 ITL P95 | 原生 K2 ITL P95 | 原生 K3 ITL P95 |

ITL 单位为 ms，使用两实例服务端直方图差值合并后按桶估算。MTP 每次输出事件可以包含多个 token。

## 后续策略对照

保持 0.95 和相同配对请求序列，分别试验短输入在单实例压力不超过 32 时统一预留 K3 状态槽，以及仅对至少 16 条序列的批次启用 GDN Prefill 分组。五次回放共 734 条请求全部正常完成。

| 流量 | 组合基线（tok/s） | 额外预留 K3 | 选择性 GDN 分组 |
| --- | ---: | ---: | ---: |
| 短输入突发 | 1275.96 | 1274.54 | 1263.09 |
| Agent 长短混合 | 357.07 | 324.15 | 283.13 |
| 逐级升降并发 | 1593.95 | 1603.02 | — |

额外预留 K3 增加了状态块占用，Agent 吞吐下降约 9.2%。选择性分组的 Agent 吞吐下降约 20.7%。本分支继续采用按需状态预留与 4096-token 多序列分组策略。上述候选结论来自单次配对回放，保留为调优记录。
