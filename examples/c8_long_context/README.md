# 910B4-1｜Qwen 27B W8A8C8 长上下文优化

这是基于 vLLM/vLLM-Ascend **0.30.0**、CANN **9.2.1** 的独立实验启动入口。目标是在保留解码整图及动态 MTP 的同时，降低混合精度 KV Cache 的管理开销、增加长历史驻留能力，并减少多个验证 token 对同一段历史 KV 的重复计算。

适用范围目前限定为单张 Ascend 910B4-1、Qwen3.8-27B W8A8C8、TP1/DP1/PP1/CP1、V2 同步调度和文本推理。经过验证的是主模型 INT8 KV、草稿 Attention BF16 KV、GDN FP32 SSM 状态的混合缓存。**本方案不需要修改 CANN，也不是整个 Attention 的原生 INT8 计算。** 未重写已安装的 vLLM、vLLM-Ascend 或 CANN 文件；只有通过本实验启动器启动的进程才加载适配层。

## 1. 启动方式

在已安装相应 vLLM、vLLM-Ascend、torch-npu、Ascend Triton、FLA NPU 26.9.1、CANN 的 Python 环境中运行，需要 GNU `patch`。模型目录应存放与实测几何一致、已完成 C8 校准的完整 checkpoint，包括 `quant_model_weights-kv-cache-c8.safetensors`。本分支不包含模型权重或校准文件，也不执行量化。

```bash
ASCEND_RT_VISIBLE_DEVICES=0 python3 examples/c8_long_context/launch.py \
  /path/to/calibrated-qwen-27b-w8a8c8 \
  --state-dir ./c8-runs \
  --served-model-name qwen-27b-c8 \
  --host 127.0.0.1 --port 8080 \
  --batch-budget 8384
```

使用 `--help` 查看完整选项；先加入 `--verify-only` 可以只校验本地版本、源码和模型配置，不启动服务。默认 8384 的分块预算适合混合冷/暖测试；如业务主要为已驻留历史的短续算，可选 `--batch-budget 8192` 作为历史基线。`--policy /path/to/policy.json` 允许自定义动态 MTP 的选档表，格式见[动态 MTP 说明](../dynamic_mtp/README.md)及 `policy.example.json`。示例表不是对所有 C8 负载的最优策略。运行目录独立创建，保存源码核对、动态 MTP 运行态及 C8 校准参数、缓存、图回放的审计日志。

启动器采用本实验已验证的参数组合：

| 参数 | 设置 |
| --- | --- |
| 张量/数据并行 | TP1 / DP1，V2 同步模式 |
| 模型与缓存量化 | BF16 模型计算类型、Ascend W8A8 权重量化、主 Attention INT8 KV、MTP 草稿层 BF16 KV |
| 最大上下文 / 最大请求数 | 262144 tokens / 64 |
| KV 预算 | `gpu_memory_utilization=0.9`，自动分配 |
| 图执行 | `mode=0`、`FULL_DECODE_ONLY` |
| MTP | 按负载选择 K=0~3，保留相应整图，启用已验证的 GDN K2 索引与 Prefill 工作空间补丁 |
| 缓存 | APC、128-token 前缀匹配单位、GDN `align` 模式、FP32 SSM、稀疏语义检查点 |
| 分块 Prefill | `max_num_batched_tokens=8192` 或 `8384`；长历史续算使用 16K LSE 分段 |
| 多 token Decode | Q4 共享历史 Attention，启用已验证的批次 1/2/4/8；其他形状沿用对应 flat/普通路径 |

不接受任意额外的 vLLM 启动参数，避免意外改变经过验证的几何、图配置或草稿精度。启动器校验两个 Python 包版本和所依赖的已安装源码 SHA-256；几何、校准参数、指针/stride 检查不通过时终止，不以其他布局冒充本方案。正式部署前需要使用自己的模型、负载、任务质量做独立验证。原生 `vllm serve` 不受影响。

如需验证新 Attention 路径在同一实际缓存上的数值结果，可在启动时加入 `--validate-fold`。该模式会在指定层图内保留小型诊断 snapshot；按启动日志提示的诊断 marker 路径开启真正的数值对照，再发出满足形状的请求。诊断只在目标图回放和参数更新均已提交之后执行，不应把开启数值对照的请求计入正式性能结果。抽样层的数值比较并不等同于独立的端到端任务准确率验证。

## 2. 优化实现

### 四组混合精度 KV Cache

主模型 16 个 INT8 Attention 层与一个未校准的 BF16 MTP 草稿 Attention 层共享逻辑块表，草稿内容保存在独立物理区域；48 个 GDN 层分为三组，每组 16 层。保持 1664-token 调度对齐和 128-token 物理 Attention 页。不要为了让缓存类型统一而强行量化草稿层，也不要让单层 BF16 草稿导致全模型每层各成一组。

对照的旧兼容布局有 65 个组，产生大量缓存元数据与图更新开销。新布局为 4 组，实测 445 个逻辑块（8192 预算）。启动时核验实际分配区域、相对偏移、精度、stride、读写页边界及 GDN view，不仅依据理论估算。

### 稀疏历史状态保留

原 Ascend 兼容层读取已经迁移的 vLLM 旧环境变量，导致实际 GDN 保留策略退回密集保留。本分支按 0.30.0 的配置恢复稀疏语义检查点保留，并按实际本地 reader 的 replay 边界选择保留位置。不创建未计算的 KV 或 GDN 状态，不修改缓存内容、引用计数或原生 cache writer。某段历史中间的任意分支复用率可能降低，适合最终历史重复续算较多的负载。

### Q4 共享历史 Attention

四个验证 Query 的公共历史相同。将多个 Query 折叠到 GQA head 轴，用现有 NPU FusedInferAttentionScore 对公共历史求 Attention 与 LSE，再用 FP32 计算且合并各自可见的极短因果尾段。尾部索引来自 Ascend V2 实际持久化 INT32 slot mapping；要求图捕获与回放的地址、dtype、实际 token 数及形状一致。正常执行不进行 device-to-host 索引同步。其他 Query 宽度、混合 Prefill 或未通过图捕获形状门控的情况走原路径；捕获后的参数不兼容则显式拒绝，不能在已捕获图中偷偷改执行拓扑。

分块 Prefill 对历史 INT8 KV 进行分页收集和 BF16 反量化，沿用现有融合 gather 以及经验证的 LSE 分段。为了减少额外的 chunk 边界，8384 预算为 5×1664-token Prefill 对齐单位再预留 64 tokens 的调度余量；不是强制每个 step 都正好 8320 tokens。10048/13376 的预算扫描未发现可靠的额外收益，且减少 KV 池，故不作为启动器默认设置。

## 3. 实测结果与适用边界

### 运行时分组与 Q4 优化

以下为真实历史完整命中、每请求正式输出 512 token、单卡的匹配对照，单位为整组输出 token/s。

| 实际历史 tokens | 并发 | 旧 C8 动态（65 组） | 四组 C8 动态 | 合并优化 C8 | W8A8 动态参考 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 46592 | 2 | 38.96 | 85.84 | — | 113.23 |
| 116480 | 1 | 17.24 | 33.86 | 48.65 | 58.30 |

独立 32 步诊断中，执行阶段中位耗时从 107.27 ms 降至 18.38 ms，普通 Attention metadata 调用从每步 17 次降至 2 次。独立原语验证 Q4 的设备执行时间如下（单层，非整模型端到端速度）：

| 形状 | flat ms | fold ms |
| --- | ---: | ---: |
| 128K 历史、C1 | 2.817 | 0.820 |
| 约 256K 历史、C1 | 5.553 | 1.314 |
| 58240 历史、C2 | 1.463 | 0.772 |
| 58240 历史、C4 | 2.756 | 2.208 |
| 58240 历史、C8 | 5.773 | 2.566 |

实际服务同缓存抽样验证覆盖已捕获的 Q4 图，最大相对 L2 误差低于 0.26%，并通过尾部地址检查。初期图适配方案曾发生 slot mapping dtype 不匹配、图更新提交前诊断同步等待等问题，最终版本修复后才进行正式比较。

### 动态 MTP 档位

同一服务内固定实际历史与完整命中，独立测试 K0–3、每请求输出 512 token，保留各档图；这是受控档位对照，不代表任意变动负载下的最优动态策略。

| 实际历史 tokens | 并发 | K0 | K1 | K2 | K3 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 116480 | 1 | 22.00 | 34.30 | 39.70 | 48.65 |
| 58240 | 8 | 100.23 | 127.24 | 138.56 | 195.06 |

稀疏保留的 63232-history 定向对照中，每条 idle 历史占用缓存块从 68 降至 41；8 条独立历史全部命中，实际同时完整 Decode 8 条且无抢占，旧密集保留的匹配条件仅部分历史命中。相同提示冷/暖单请求的 512 个 token ID 完全一致；它不代表其他任务一定逐 token 一致。

### 同提供负载的 W8A8 / W8A8C8 对照

58240 历史 + 512 新输入（58752 实际输入），并发 8，实际 K3，512 输出/请求，双方相同输入、0.9 自动池、稀疏保留、8192 批预算。每组均完整输出 4096 tokens，无抢占。

| 场景 | W8A8 整组输出 tok/s | C8 整组输出 tok/s | W8/C8 完整历史命中 |
| --- | ---: | ---: | ---: |
| 冷：前缀命中为 0 | 26.33 | 25.39 | 0/8、0/8 |
| 暖：独立历史预建后 | 32.96 | 195.06 | 2/8、8/8 |

暖场景 TTFT P50（秒）37.56→2.94，P95 114.48→3.03。两种精度面对的是相同的提供负载，但由于容量不同实际命中率不同：暖场景约 5.9 倍吞吐来自真实缓存驻留能力与运行时优化的共同提升，**不是相同缓存命中率下 Attention 算子的普遍速度比值**。冷场景略低于 W8A8，收益集中在长历史高并发复用。

### 冷 Prefill 预算扫描

同一 8 请求冷负载、零前缀命中、每请求 512 输出，C8 保持其余优化不变，记录自动 KV 池。

| 批 token 预算 | 整组输出 tok/s | C8 逻辑块池 |
| ---: | ---: | ---: |
| 8192 | 25.393 | 445 |
| 8384 | 26.253 | 444 |
| 10048 | 26.295 | 439 |
| 13376 | 25.985 | 429 |

8384 暖回归为 188.74 tok/s，全部 8 条历史命中，对照 8192 的 195.06 tok/s；峰值/回归均来自单组测试，不能断言微小差异来自预算本身，也不宣称超过重新调优后的 W8A8。另行采集的 C1 全 Prefill profile 仅统计实际处理 58752 输入 tokens 至后续 Decode 前：W8A8/C8 设备 kernel 累计 15.672/15.794s，C8 gather/dequant 累计约 29ms。后续不应把主要计算瓶颈简单归为反量化。

## 4. 如何理解发布范围

- 这是可复现的候选运行时适配，不是通用 vLLM-Ascend 正式 API。发布入口默认不捕获诊断 snapshot；历史对照的候选图仍含两个选定层的小型 snapshot 复制，正式请求关闭数值比较 marker，因此性能数据是有明确范围的参考记录，不是此发布入口重新压测的成绩。
- 当前只验证单卡、该模型和准确的源版本；尚未验证 TP2/DP2 的组合性能、Mooncake 持久缓存与本布局的同时启用、多模态、长期实际流量或各类任务的精度。
- 采用同一模型、相同负载、实际输出数、实际命中率和真实图状态核验，不使用不同精度下的理论 token 容量直接推导服务性能。
- 外部 vLLM 改动、Ascend 改动及 CANN 边界见[跨仓库源码映射与版本记录](SOURCE_MAP.zh-CN.md)。此前未通过验证的原生全 INT8 Attention 研究不包含在此分支。
